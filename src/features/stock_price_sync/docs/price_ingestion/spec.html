Stock Price Sync — Price Ingestion
Minute-cadence per-ticker FMP 1-min chart fetch · current-session snapshot derivation · idempotent Firestore overwrite

Every minute from 9:30am to 4:05pm ET on weekdays this pipeline reads the global watchlist, fetches each ticker's current-session 1-minute chart from FMP (one API call per ticker — the endpoint does not support multi-symbol queries, and quote endpoints are not available on the current FMP plan), derives a compact price snapshot (latest price, change vs previous close, sparkline series), and overwrites stock_prices/{ticker} in Firestore. Bars are near-real-time (the 1-min chart endpoint is not subject to the plan's 15-min quote delay), and the 4:05pm final run captures the complete session including the 4:00pm close.

FunctionTriggerSchedule
stockPriceSyncCloud Scheduler* 9-16 * * 1-5 (America/New_York), gated in code to 9:30am–4:05pm ET
The keystone property: each run writes a complete, self-contained snapshot of the current session. Nothing is appended, accumulated, or cursored. Any failure — one ticker, one run, a whole outage — is fully repaired by the next successful run, at most 60 seconds later. Retries, queues, and dead-letter handling are structurally unnecessary: the schedule is the retry.

Entry Point — stockPriceSync

Instantiates service dependencies at module scope (single composition root) and delegates to the use case. Contains no business logic. FMP_API_KEY is declared with defineSecret('FMP_API_KEY') and bound via secrets: [fmpApiKey].

Operational kill switch: no Remote Config flag — pause/resume the Cloud Scheduler job in the GCP console. Resuming is trivially safe: the first run after a pause rebuilds every snapshot from scratch — no catch-up logic, no gap to repair.
The 9:30–4:05 window: the regular session is 9:30am–4:00pm ET and the 1-min endpoint serves bars near-real-time (verified — no 15-minute delay on this endpoint). The window opens with the session, and the last run at 4:05pm captures the complete session including the 4:00pm close bar. No extended-hours data on the plan, so there is no premarket window to widen into.
  1. Reads process.env.FMP_API_KEY; if missing, logs an error and returns (no retry — misconfiguration is not transient).
  2. Instantiates StockPriceSyncUseCase with FmpChartService, FirestoreService, and the core FirebaseWatchlistService, then calls execute() — its step 1 applies the market-window gate.
  3. On use-case error: logs and swallows it. The scheduler fires again in ≤ 60 seconds and the next run rebuilds every snapshot.

Orchestration — Use Case Steps

Steps 1–3 run sequentially; step 4 processes tickers concurrently under a fetchConcurrency limit with per-ticker error isolation (Promise.allSettled semantics). Nothing is fire-and-forget.

  1. Market-window gate — current ET time outside 9:30am–4:05pm → debug log and return (a gated exit costs milliseconds and zero FMP calls).
  2. Load watched tickers — core FirebaseWatchlistService.getAllWatchedTickers() → Map<ticker, companyName>, cached at module scope for watchlistCacheSeconds (default 300s). Empty map → return. Fetch failure after retries → log error and return; the next minute retries.
  3. Select cohort — maxCallsPerRun = 0 (default — 1,500 calls/min Enterprise quota leaves ~3× headroom at 500 tickers) → all tickers. Otherwise numCohorts = ceil(N / maxCallsPerRun), sorted tickers, keep index % numCohorts === minuteOfDay % numCohorts. Deterministic, stateless, balanced.
  4. Per ticker (concurrency ≤ fetchConcurrency, default 8):
    1. Resolve previous close & fetch — module-scope Map<ticker, {sessionDate, previousClose}>. Cache hit for today → today-only fetch (from = to = today). Miss (first run of day, cold instance, new ticker) → narrow seed fetch (from = today − 3 on Mondays to reach Friday, today − 1 Tue–Fri); if the response has no session before today (holiday/ad-hoc closure), retry once widened (from = today − seedFallbackCalendarDays, default 6). previousClose = final bar close of the latest session before today (null if still none), cached under today's date — even when the result is null or today has no bars yet, so one seed sequence per ticker per day. Failure after retries → logged, counted, continue.
    2. Build snapshot — keep only bars whose date prefix equals today's ET date; sort ascending; sessionDate = today, price/latestBarAt = newest raw 1-min bar; change/changePercent from previousClose (null when unavailable). series = bars downsampled into seriesBucketMinutes buckets (default 5; bucket = floor(minutes-since-midnight ÷ size), one {t, c} point from each bucket's newest bar, in-progress bucket included — the series tip always equals price). No today bars (holiday, new listing) → skip, doc untouched.
    3. Skip if unchanged — module-scope Map<ticker, latestBarAt>; equal → no write. Cache set only after a successful write.
    4. Upsert — full-overwrite set() on stock_prices/{ticker} + updatedAt server timestamp. Failure → logged, counted; next run rewrites.
  5. Summary log — written/skipped/failed of total + duration ms. Duration > 45s logs at WARN — the watchlist has outgrown the concurrency/timeout budget.
Retention note: "current session only" applies to what a write contains, not when documents vanish — overnight, on weekends, and on holidays there is nothing new to write, so each document retains the last completed session and the front end simply renders the latest available data (resolved decision). sessionDate identifies the session.

Failure Isolation

FailureEffect
Single ticker FMP fetch fails after retriesLogged, counted; other tickers unaffected; refreshed by the next run (stale ≤ 60s)
Seed fetch failspreviousClose not cached → next run retries the seed; ticker skipped this run
Single document write failsLogged, counted; unchanged-skip cache not updated → next run rewrites it
Watchlist read fails after retriesRun aborts with error log; next minute retries; documents keep their last snapshot
FMP outageRuns fail fast and log; first successful run rebuilds every snapshot in full — no gap-repair or backfill
Function crash mid-runEvery document still internally consistent (single-doc atomic writes); next run completes the rest
Instance restartBoth in-memory caches (previousClose, latestBarAt) rebuild next run: one seed fetch + one redundant write per ticker (~25 MB, ~500 writes) — negligible
Overlapping runsPrevented by maxInstances: 1; a race would still be safe — both write full valid snapshots, last-write-wins is correct

Domain Types

interface IntradayBar {
  date: string;      // "YYYY-MM-DD HH:mm:ss" — US/Eastern, lexicographically sortable
  open: number;
  low: number;
  high: number;
  close: number;
  volume: number;
}

interface PricePoint {
  t: string;         // "HH:mm" ET of the bucket's newest bar — sessionDate supplies the date
  c: number;         // that bar's close
}

interface PriceSnapshot {
  ticker: string;                 // uppercase
  companyName: string;
  price: number;                  // close of the newest 1-min bar of the current session
  previousClose: number | null;   // final bar close of the prior trading session (daily seed fetch)
  change: number | null;          // price − previousClose
  changePercent: number | null;   // change / previousClose × 100
  sessionDate: string;            // "YYYY-MM-DD" (ET) — always the current session at write time
  series: PricePoint[];           // current session, downsampled to seriesBucketMinutes buckets (~79 pts at 5 min)
  latestBarAt: string;            // newest 1-min bar date — unchanged-skip key
}

date strings are compared lexicographically everywhere; nothing is parsed to Date except the market gate and window-date computation, done in America/New_York like stock_news_notifier. change/changePercent measure the day's move against the prior session's final 1-min bar close (≈ official close ± a cent or two) from the daily seed fetch; both are null when previousClose is unavailable.

Firestore Schemas

watchlist/{ticker} — read

Written by watchlist_aggregator, read via the core FirebaseWatchlistService: ticker (doc ID), companyName, lastAddedAt.

stock_prices/{ticker} — written

StoredStockPrice — PriceSnapshot plus updatedAt. Full-overwrite set() (never merge): the document is a pure projection of the latest FMP fetch. series only ever contains the current session, downsampled server-side to seriesBucketMinutes buckets — ~79 points ≈ 2 KB at the default 5 min (visually identical on a mini sparkline, which has fewer horizontal pixels than points; a future full-resolution detail chart fetches FMP separately or lowers the knob). One doc per ticker, bounded by watchlist size — no TTL, no cleanup.

Front-end read pattern. One-time fetches on home-tab view or pull-to-refresh — no continuous listeners (a deliberate cost decision: read volume scales with user activity, not with market-hours write volume). Direct document reads, no queries, no composite indexes:

db.collection('stock_prices').doc(ticker).get()   // one get per watched ticker per refresh
Outside market hours the document holds the last completed session and the front end simply renders the latest available data — sessionDate identifies the session.

Two fetch modes

The window is chosen per call by the use case; the today-only default keeps the feature at ~18% of the plan's 500 GB / rolling-30-day bandwidth cap (a multi-day window every minute would total ~570 GB/30d):

ModeWindowWhenPayload
Today-only (~99% of calls)from = to = todaypreviousClose cached for today0→43 KB, growing through the day
Seed — narrowfrom = today − 3 Mondays (reaching Friday), today − 1 Tue–FriFirst run of day, cold instance, new ticker~45 KB, once per ticker per day (~25 MB/day — negligible)
Seed — widened fallbackfrom = today − seedFallbackCalendarDays (default 6)Narrow seed found no prior session (holiday / ad-hoc closure)~130–250 KB, one extra call/ticker on ~9 post-holiday mornings/year
The weekday rule handles the predictable calendar (weekends); the widen-on-miss fallback handles the unpredictable one — the market data itself is the holiday calendar. "No prior session in the response" is exactly what a closure looks like, so the fallback is always right, including for ad-hoc closures (presidential funerals) no holiday package can predict. This is why the pipeline carries no holiday-calendar dependency.

fetchIntradayBars(ticker, window): fetches once (no pagination), validates rows at the boundary (drops rows missing a string date or finite close, one info log per ticker), returns unsorted validated bars — sorting, session filtering, and previousClose derivation belong to the use case. Empty array is valid (holidays, new listings). Retry per fetch: maxAttempts 3, initialDelayMs 1000, backoffFactor 2; non-ok and non-array responses throw and are retried.

Service — firestore_service

upsertPrice(snapshot) — full-overwrite set() on stock_prices/{ticker} with updatedAt: serverTimestamp(). Never merge (stale fields would survive shape changes and break the idempotency argument). Throws on failure — isolation and counting live in the use case; no in-process retry, the next run's rewrite is the retry. No transactions, no state documents, no delete path (watchlist is append-only).

Remote Config — stock_prices_config

Created with the JSON data type (like stock_news_config), parsed into AppConfig.stock_prices:

stock_prices: {
  fetchConcurrency: number;       // default 8    — parallel FMP calls
  maxCallsPerRun: number;         // default 0    — 0 = all tickers/run; > 0 = round-robin cohorts
  watchlistCacheSeconds: number;  // default 300  — per-instance watchlist cache TTL
  seriesBucketMinutes: number;    // default 5    — series downsample bucket; 1 = every raw bar
  seedFallbackCalendarDays: number; // default 6  — widened seed window when the narrow seed finds no prior session
}

All knobs runtime-adjustable without a deploy. No enabled flag — pausing the Cloud Scheduler job is the kill switch.

Design Decisions — Why Not Pub/Sub

The original plan (scheduler → per-ticker Pub/Sub messages → subscriber makes the API calls, "in case of failures") correctly identified the forced per-ticker fan-out. The Pub/Sub layer is rejected:

ConcernAnalysis
Retries are anti-valueA redelivered message executes minutes later, delivering data the next scheduled run has already superseded. Every retry is wasted work racing a fresher full refresh.
Rate limiting gets worseFan-out across auto-scaled subscribers makes aggregate FMP concurrency unbounded → thundering-herd 429s. One function + fetchConcurrency + maxCallsPerRun is precise and Remote-Config-tunable.
Cost & noise~720k invocations/day (publishes + subscriber runs + topic/DLQ/monitoring) vs ~481/day.
Duplicate/ordering hazardsAt-least-once delivery can overwrite fresher snapshots with staler ones unless writes carry version guards — complexity defending against a self-inflicted problem.
Contrast with weekly_recap, where Pub/Sub is justified: minutes of LLM work per message on a weekly cadence — a lost company is a lost week. Here the unit of work is a ~300ms GET refreshed ~390×/day; losing one costs 60 seconds of staleness. Revisit if per-ticker work ever becomes expensive and loss-intolerant.
  • Full-session snapshot, not quote-tick accumulation — quote endpoints unavailable (confirmed 2026-07-16); accumulation would also need gap/seed/backfill logic. If batch-quote ever becomes available: batch-fetch prices per minute, drop this pipeline to a lower cadence for series — the doc shape already supports the split.
  • Two-mode fetch window — driven by the 500 GB/30d bandwidth cap: today-only fetches ~99% of the time, one seed per ticker per day for previousClose on the same endpoint (in-memory daily cache, ~25 MB/day). No second endpoint, no stored state. Caveat: the prior session's final 1-min bar close ≈ official close ± a cent or two — acceptable for a watchlist row.
  • Seed window: weekday-aware narrow fetch + widen-on-miss fallback, no holiday calendar — the narrow seed reaches one calendar step back (today − 3 Mondays, today − 1 otherwise); if no prior session is present, one widened retry (today − seedFallbackCalendarDays) recovers it. Rejected a holiday package: generic ones are wrong for NYSE (Good Friday closed; Columbus/Veterans Day open) and none predict ad-hoc closures — the market data is the calendar. Also rejected the original fixed 4-day window: correct but ~3× the daily seed payload for one small branch.
  • Current session only in Firestore; documents never blanked — outside market hours each doc retains the last completed session and the front end renders the latest available data; sessionDate identifies the session.
  • No lease, no state doc — unlike stock_news_notifier, there is no cursor to corrupt; maxInstances: 1 suffices and last-write-wins is correct.
  • Embedded series array, not a points subcollection — one read, atomic replace; a subcollection costs one read per point per chart render.
  • Series downsampled server-side to 5-min buckets — a mini sparkline has fewer horizontal pixels than a session has 1-min bars, so raw storage ships ~5× the bytes for zero visual gain; each bucket contributes its newest bar, in-progress bucket included so the series tip equals price.
  • Cron + in-code gate — a single cron expression cannot express 9:30/4:05 boundaries; a gated exit costs milliseconds and zero FMP calls.
Consistency guarantees: Documents — always internally consistent (atomic full overwrite). Freshness — ≤ 60s behind the FMP feed in-session. Recovery — unconditional: any failure heals on the next successful run, no operator action.
